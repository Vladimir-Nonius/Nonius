# Архитектура Nonius

Ядро на Rust связывает CAD, людей и ИИ через одну папку проекта. Источники только поставляют файлы; хранение, сравнение и заметки — в ядре и модулях; интерфейс общается с ядром через локальный API.

```
 Аддин SolidWorks      Любой CAD            ИИ-агенты
 (C#: STEP, SLDPRT,    (Компас, Fusion,     (MCP, API, CLI)
  дерево)               FreeCAD: STEP)
        │                    │                    ▲▼
        ▼                    ▼                    │
 ┌─────────────────── Программа на Rust ───────────────────┐
 │  Хранилище версий          │  Сравнение                 │
 │  git + LFS, файлы/ссылки   │  OpenCascade через FFI     │
 │  история, варианты, откат  │  числа, подсветка, дерево  │
 │────────────────────────────┼────────────────────────────│
 │  Заметки и ссылки          │  API и MCP                 │
 │  Markdown, [[ссылки]]      │  синхронизация с сервером  │
 └──────────────────────────────────────────────────────────┘
        ▲▼                   │                    ▲▼
 Папка проекта          Окно программы       Сервер проекта
 STEP, YAML, Markdown   (egui, в nonius.exe) Forgejo: роли, блокировки
```

Какой файл за что отвечает — в [CODEMAP.md](CODEMAP.md).

## Папка проекта

```
мой-проект/
├── project.yaml            # имя, участники, роли, допуски сравнения
├── AGENTS.md               # описание проекта и правила для ИИ
├── .gitattributes          # бинарные файлы CAD через Git LFS
├── Стена/                  # папка-группа: обычная папка, уровней сколько угодно
│   ├── .gitkeep            # держит в git пустую папку
│   └── PANEL-00/           # деталь или сборка — папка с meta.yaml
│       ├── meta.yaml       # вид (деталь/сборка), масса, объём, габариты, материал, свойства
│       ├── tree.yaml       # дерево построения (если из SolidWorks)
│       ├── model.step      # геометрия, есть всегда
│       ├── model.sldprt    # исходник
│       ├── preview.png
│       └── docs/           # чертежи, PDF, DXF
├── RAIL-01/                # деталь может лежать и прямо в корне
└── notes/                  # заметки Markdown со ссылками [[деталь@v3#Фича]]
```

Дерево проекта — это папки на диске, один к одному (как хранилище Obsidian). Отдельного списка «какая деталь где» нет: деталь — любая папка с `meta.yaml`, внутрь детали обход не заходит, остальные папки — группы (`nonius_core::project::layout`). Вид детали берётся из её `meta.yaml`. Имя детали уникально во всём проекте: это её имя в истории (`Nonius-Item`), а место может меняться. Карту для программ и ИИ даёт `nonius map --json`.

До `project.yaml` схемы 2 детали лежали в `parts/<имя>/`, сборки — в `assemblies/<имя>/`. Такой проект открывается только для просмотра (`Project::writable` → код `old_layout`), окно один раз спрашивает «Обновить?», команда — `nonius upgrade`. Обновление (`Store::upgrade`) — одна запись истории: `git mv` каждой детали в корень (несохранённое переезжает и остаётся несохранённым), `project.yaml` схемы 2 и строка `Nonius-Layout: 2`. Если что-то не получилось (папка с таким именем уже есть, файл занят), всё возвращается как было.

Каждый файл данных начинается с `schema: N` (`nonius_core::schema`). Программа читает свою и более старые схемы (через миграции) и отказывается читать более новые, чтобы не испортить файл.

## Ядро и модули

Ядро (`nonius-core`) — только формат проекта, схемы, имена, точки расширения и реестр. Всё остальное — модули, и встроенные подключаются так же, как сторонние.

| Точка (`ExtensionPoint`) | Трейт | Что делает | Примеры |
|---|---|---|---|
| `GeometrySource` | `GeometrySource` | файл → паспорт версии (`meta.yaml`) | STEP через OpenCascade, SLDPRT без SolidWorks |
| `TreeSource` | `TreeSource` | файл → дерево построения | аддин SolidWorks, FreeCAD |
| `Comparator` | `Comparator` | различия двух версий | паспорт (встроен: `meta-compare`), геометрия, дерево, BOM |
| `Renderer` | `Renderer` | картинки и GIF изменений (`render_with` получает допуск проекта) | цветная подсветка |
| `Exporter` | `Exporter` | файлы из версии | DXF, PDF, STL |
| `Converter` | `Converter` | файл CAD → STEP при импорте | SolidWorks (встроен: `solidworks-step`) |
| `Links` | `LinkSource` | связи файлов: сборка → детали, чертёж → модель | SolidWorks (встроен: `solidworks-links`), позже аддин |
| `Events` | `EventHandler` | реакция на события | уведомления в Telegram, проверки перед утверждением |
| `Ui` | — | панели интерфейса | подключаются веб-интерфейсом |

Правила, чтобы модули ничего не ломали:
- у модуля `ModuleManifest`: id, название, версия, версия API, точки, права;
- реестр подключает модуль только к точкам из манифеста и проверяет версию API (`API_VERSION`, `MIN_API_VERSION`);
- права явные (`Permission`);
- для каждой точки есть контрактная проверка в `nonius_core::contract`; модуль, прошедший её, совместим;
- ядро не знает о конкретных модулях; отключение модуля не теряет данные — они в открытых форматах.

Способы подключения: встроенный крейт (сейчас), внешний процесс по JSON-RPC и WASM-модуль (позже).

### Файл SolidWorks без ручного STEP (`nonius-solidworks`)

`.sldprt` — закрытый формат: Nonius хранит его как есть, а форму, массу и сравнение считает по STEP. Чтобы человек не выгружал STEP руками при каждом импорте, есть точка `Converter`: при импорте `.sldprt` / `.sldasm` модуль получает STEP, и импорт кладёт его рядом как `model.step` — дальше всё идёт обычной дорогой STEP (паспорт, превью, сравнение).

```
 nonius import вал.sldprt
   └─ nonius-app import.rs ── Converter::to_step ──► nonius-solidworks
                                                       └─ powershell export_step.ps1
                                                            └─ SolidWorks (COM): открыть → «сохранить как STEP» → закрыть
   ◄── model.step во временной папке ── паспорт из STEP ── model.sldprt + model.step в деталь
```

- Модуль `solidworks-step` подключается, только если SolidWorks установлен (запись `SldWorks.Application` в реестре Windows). Нет SolidWorks — импорт работает как раньше и предупреждает, что STEP прежний.
- Разговор идёт через скрипт PowerShell, а не из Rust: так не нужен `unsafe` и новые зависимости. Скрипт зашит в программу.
- Вежливость к человеку: открытый SolidWorks не закрывается и его настройки не меняются; деталь с несохранёнными правками не выгружается («сохраните и повторите»); запущенный нами SolidWorks невидим и закрывается за собой — не сразу, а после полуминуты простоя. За этим следит сторож (`close.ps1`), отдельный маленький процесс: невидимый SolidWorks сам завершается, когда от него отключилась последняя программа, поэтому сторож подключается первым и держит его, пока идёт работа. Пять деталей подряд — 30 с вместе с запуском, а не по 15 с на каждую.
- Перевод не удался — это предупреждение, а не ошибка: файл всё равно импортируется.
- Время (деталь на 350 граней): около 3 с при открытом SolidWorks, около 20 с, если его приходится запускать.
- Две найденные на практике ловушки записаны в скрипте: короткая запись вызовов PowerShell ломается на битом описании типов SolidWorks (поэтому `InvokeMember`), а деталь, открытая без окна в невидимом SolidWorks, роняет его модуль выгрузки STEP (поэтому без окна — только в открытом).

## Хранилище версий (`nonius-store`)

Версия детали — коммит git, который меняет только папку этой детали. В сообщении — описание и служебные строки:

```text
кронштейн v3: толщина 4 → 5 мм под новый вал

Nonius-Item: кронштейн
Nonius-Version: v3
```

- номер версии у каждой детали свой и растёт на 1;
- бинарные файлы идут через Git LFS по `.gitattributes`, файлы версии читаются `git cat-file --filters`;
- откат (`restore`) создаёт новую версию с содержимым старой — история не переписывается;
- удаление и переименование детали — отметки в истории (`Nonius-Deleted`, `Nonius-Renamed`, `Nonius-Recovered`), а не версии: удалённая деталь возвращается, версии идут за деталью через переименования, новая деталь со старым именем чужих версий не получает;
- перенос детали в другую папку — отметка `Nonius-Moved: <прежний путь>`; у удалённой детали `Nonius-Folder` — где она лежала, туда она и возвращается. Папку каждой версии `lineage.rs` прослеживает назад по этим отметкам, переименованиям и записи `Nonius-Layout` (до неё — `parts/<имя>` или `assemblies/<имя>`), поэтому старые версии читаются после любых переносов, а история не переписывается;
- используется системный `git`, а не библиотека: он уже умеет LFS и ведёт себя одинаково у всех.

## Действия программы (`nonius-app`)

Командная строка, окно и (позже) MCP вызывают одни и те же действия `nonius-app::App`: детали со статусом, история, сохранить версию, откат, выгрузка, импорт, паспорт, сравнение. `nonius-app` ничего не печатает и не знает о конкретных модулях: реестр собирает вызывающий. `App` можно делить между потоками — окно вызывает долгие действия в фоне, передавая `Progress` (шаги и отмена).

**Масса** = объём × плотность и считается только при заданном материале. Материал и плотность (`density_kg_m3`) лежат в `meta.yaml` и попадают в версию. Плотность берётся из справочника частых материалов или вводится вручную; «по умолчанию» не подставляется. Без материала программа так и пишет: масса не посчитана.

**Кэш сравнений** — `.git/nonius/cache/<ключ>/`, в историю не попадает. Ключ — хеш обеих версий (коммит; для текущего состояния — пути, размеры и время изменения файлов), допусков и версий модулей. Хранятся 200 последних записей, старые удаляются — кэш всегда можно пересчитать. Отчёты и файлы отрисовщиков (`changes.png`, `changes.glb`) кэшируются отдельно. Описание записи `cache.yaml` начинается с `schema: N` и меняется только с миграцией; незнакомая, битая или неполная запись пересчитывается. Запись готовится во временной папке и ставится на место одним переименованием (`nonius_store::workdir`, так же выкладываются версии).

## Цвета подсветки

`ChangeKind` в отчёте сравнения привязан к цвету: `Added` — зелёный, `Removed` — красный, `Moved` — жёлтый, без изменений — приглушённый.

## Окно программы (`nonius-gui`)

Двойной щелчок по `nonius.exe` (или `nonius view [деталь] [было] [стало]`) открывает окно: детали проекта, выбор версий «Было» и «Стало», деталь в 3D с цветной подсветкой изменений, список мест изменений, числа из паспортов. Окно — часть того же exe, без браузера, ничего не нужно ставить. Командная строка работает как прежде; `NONIUS_NO_WINDOW=1` вместо окна печатает подсказку (серверы, проверки).

Окно получает проект через трейт `nonius_gui::source::ProjectSource`; реализация поверх `nonius-app` лежит в `nonius-cli/src/window/source/` (`AppSource`). Поэтому окно и команды берут сравнения из одного кэша. Для окна реестр собирается без картинки `changes.png` (`nonius_occt::register_for_window`): ему нужна только сцена. Сравнения идут по одному: OpenCascade не терпит параллельного чтения STEP. Долгое сравнение можно отменить: окно сразу свободно, расчёт бросается между шагами; шаг, который успел досчитаться, остаётся в кэше — второй раз он не считается. В окне же — история детали, сохранение версии с обязательным описанием, материал (справочник или своя плотность) и масса «было → стало»; всё это — те же действия `nonius-app`, что у команд `commit` и `material`.

### Вкладки проектов и черновик

Проекты открываются вкладками, как в браузере. Всё, что окно знает об одном проекте (детали, версии, сравнение, окошки), лежит в `ProjectTab`; у каждой вкладки своя очередь фоновых работ, поэтому результат не попадает в чужую вкладку. Рисуется только открытая вкладка, остальные ждут. Один проект в одном окне: замок `.git/nonius/window.lock` (`nonius-cli/src/window_lock.rs`) не даёт открыть его во втором окне, а в этом окне повторное открытие просто переходит к его вкладке.

Папка для начала работы не нужна. «Новый проект» (и запуск без открытых вкладок) создаёт черновик — обычный проект Nonius с git, только во временной папке программы `%LOCALAPPDATA%\Nonius\drafts\<метка>\Без имени`. Второй системы хранения нет: черновик отличается от проекта лишь местом на диске. «Сохранить проект как…» переносит папку целиком, с историей, в выбранную пустую папку (`nonius_app::move_project`): на том же диске — переименование, на другом — копия и удаление; название проекта становится именем папки. Перенос ждёт, пока закончатся все потоки вкладки, даже отменённые: они держат файлы проекта открытыми. Закрыть вкладку или окно с несохранённым черновиком, где есть детали, можно только после вопроса; «Не сохранять» отправляет черновик в Корзину (правило «ничего не удаляется»), пустой черновик стирается.

Проект старого формата (`parts/`, `assemblies/`) окно открывает только для просмотра: при открытии один раз спрашивает «Обновить?» («Не сейчас» / «Обновить»), дальше над проектом остаётся жёлтая полоса с той же кнопкой (`app/upgrade.rs`). Обновление ждёт, пока вкладка свободна, и открывает проект заново.

### Выделение → команда → очередь

Дерево и «Структура» называют предметы одним словом — `Node` (деталь, папка, файл папки) — и делят одно выделение (`app/selection.rs`): отмеченное в одном виде подсвечено и в другом. Клавиша, пункт меню и перетаскивание не делают работу сами, а просят одну команду (`app/command.rs`: удалить, перенести, выделить всё, снять выделение, переименовать, открыть); что она значит для одного предмета и для нескольких, решается там же. Клавиши выделенного (Delete, Ctrl+A, Esc, F2, Enter) слушаются в конце кадра и только когда ни один виджет не держит клавиатуру, не открыто окошко и не открыто меню. В окошке с кнопками главная кнопка сразу в фокусе и ←/→ выбирают соседнюю; в открытом меню ↑/↓ ходят по пунктам по кругу (`app/choice.rs`: стрелки окно забирает раньше egui, иначе egui двигает фокус на два пункта и за край меню). Несколько предметов идут очередью (`app/batch.rs`): одна фоновая работа, предметы по одному, ход «Переношу 3 из 5: …» и «Остановить» (после текущего) в строке состояния; итог — одной строкой, ошибки — по строке на предмет. Очередь не отменяется выбором другой детали, а запись в проект и так идёт по очереди (`writing()` в `nonius-cli/src/window/source`).

Окно получает эти действия так же, как открытие и создание проекта, — замыканиями в `nonius_gui::Options` (`opener`, `creator`, `mover`, `discard`): `nonius-gui` не знает про git, файловые операции и Корзину.

Окно помнит открытые вкладки и переключатели вида в `%APPDATA%\Nonius\window.txt` (Linux — `~/.config/nonius/window.txt`): строки `tab=<папка>` по порядку и `active=<номер>`; строка `last_project` из прежних версий читается как вкладка. Испорченный файл не мешает запуску, пропавшие папки пропускаются.

### Крейты и границы

```
 nonius-cli (exe) ──┬── nonius-gui ──┐       окно: egui + wgpu
   команды,         │                ├── nonius-app     действия программы
   сборка реестра   └────────────────┘        │
   модулей                                    ├── nonius-store   версии: git + LFS
                                              ├── nonius-scene   модель сцены и glTF
                                              └── nonius-core    формат, схемы, точки расширения
 модули: nonius-occt (OpenCascade), nonius-step, nonius-solidworks … — подключаются к реестру из nonius-core
```

| Крейт | Что внутри | Чего не знает |
|---|---|---|
| `nonius-core` | формат проекта, схемы, точки расширения, реестр | окна, git, OpenCascade |
| `nonius-scene` | модель сцены: слои, сетки, места изменений, подписи; запись и чтение glTF (`.glb`) | OpenCascade, egui, git |
| `nonius-app` | **действия**: открыть проект, детали, история, сравнить (с кэшем и в фоне), импортировать модель, сохранить версию, откатить, выгрузить, задать материал | окна и консоли |
| `nonius-gui` | окно: панели, 3D-вид, мышь, фоновые задачи, тексты интерфейса | OpenCascade и git: всё через `nonius-app` |
| `nonius-cli` | разбор команд и печать; собирает реестр со встроенными модулями и передаёт его в `nonius-app`; без команды открывает окно | — |

Правила:
- CLI, окно, а позже MCP и сервер вызывают **одни и те же действия** `nonius-app`. Логика не дублируется: что умеет окно, умеет и команда, и ИИ.
- `nonius-core` не тянет графику: в ядре нет egui, wgpu и glTF.
- Отрисовщик (`Renderer`) отдаёт сцену файлом `changes.glb`. Окно читает его через `nonius-scene` и не знает, каким модулем и из какого CAD-формата он сделан. Сменить движок отрисовки окна или добавить новый формат — работа одного крейта.
- Будущие панели модулей (калькулятор массы, раскрой листа) подключаются к точке `Ui` через трейт панели в `nonius-gui`. Трейт появится вместе с первым таким модулем.

### Модель сцены (`nonius-scene`)

Сцена — то, что показывается в 3D:
- **место** — кусок материала с ролью, сеткой и объёмом. Роли: `after` (новая версия целиком, «стало»), `before` (старая версия целиком, «было»), `added`, `removed`, позже `moved`. Каждый отдельный кусок добавленного или убранного материала — своё место: по списку мест окно приближает к изменению;
- цвет роли один для картинок, 3D и интерфейса (`Role::color`);
- сетки в мм, оси — как в исходном файле (у SolidWorks Y вверх).

На диске сцена хранится в стандартном glTF 2.0 (`.glb`): узел на каждое место, роль и объём лежат в `extras`. Старая версия целиком лежит во второй сцене glTF, поэтому сторонние программы (Средство 3D-просмотра Windows, Blender) показывают «стало» с цветными изменениями.

**Формат сцены и формат кэша — публичный контракт с номером версии**, как схемы файлов проекта:
- в `asset.extras.nonius_scene` у `.glb` записан номер формата сцены; в `cache.yaml` — `schema: N`;
- новые поля добавляются так, чтобы старые программы их пропускали; несовместимое изменение повышает номер и идёт с миграцией и тестом на старый файл;
- более новый формат программа не читает и объясняет, что пора обновиться;
- `nonius_scene::contract` проверяет сцену любого модуля-отрисовщика (роли, сетки, единицы, номер формата). Её прогоняют тесты `nonius-scene` без OpenCascade и тесты каждого отрисовщика; в репозитории лежит образец `.glb` каждой версии формата, и новые программы обязаны его читать.

### Поток данных при сравнении

```
окно: выбрали «было» и «стало»
  → nonius-app: ключ кэша = хеш обоих model.step + версии модулей
      ├─ есть в кэше → сразу отчёт и сцена
      └─ нет → фоновая задача с ходом выполнения и отменой:
            реестр: сравнения (отчёт) ‖ отрисовщик сцены (changes.glb)
            → записать в кэш
  → окно: 3D, места изменений, числа
```

Правила честности сравнения формы (`nonius-occt/src/modules/diff.rs`):

- **Шум — по толщине куска, а не по доле объёма детали.** Булевы операции оставляют плёнки вдоль совпадающих граней; плёнка тоньше допуска проекта — шум. Толщина куска = объём / половина площади. Раньше шумом считалось всё меньше миллионной доли объёма детали, и в большой детали пропадало настоящее маленькое отверстие.
- **Один допуск на отчёт, картинку и сцену.** Программа зовёт отрисовщики через `Renderer::render_with` с допуском проекта, поэтому булева разница считается один раз и рисунок совпадает с числами.
- **Проверка баланса на всех трёх путях** (местная разница → тела целиком → два вычитания): «было + добавлено − убрано = стало». Не сошлось и на последнем — разница показывается со строкой «Сравнение формы приблизительное».
- **Нет твёрдых тел — так и сказано.** Файл из одних поверхностей даёт строку «Форма не сравнена», а не пустой отчёт.
- **Отказ запоминается** так же, как удача: сцена и картинка не повторяют за сравнением тот же долгий расчёт с тем же концом.

Кэш лежит в `.git/nonius/cache/` и в историю не попадает. Описание кэша `cache.yaml` начинается с `schema: N` и меняется только с миграцией, как все схемы. Незнакомую или битую запись программа пересчитывает и ничего не теряет.

### Тексты интерфейса

Все надписи окна собраны в одном модуле `crates/nonius-gui/src/texts.rs`: таблица строк, русский по умолчанию. Код окна берёт надписи только оттуда. Перевод на другой язык — ещё одна такая таблица; если языков станет много, таблица переедет в файлы готового формата (Fluent), а код окна при этом не поменяется. Сторонняя библиотека переводов сейчас не нужна: лишние зависимости в одном exe ни к чему.

### Как устроен 3D-вид

- Камера ортогональная, как в CAD (`view/camera.rs`): виды, вращение вокруг центра детали, масштаб к курсору, «целиком», плавный переход между видами.
- Отрисовка (`view/gpu/`) идёт на видеокарте в отдельную картинку, которую окно показывает как изображение; та же отрисовка сохраняет PNG («Сохранить картинку») и работает в тестах без окна. Сглаживание краёв — 4 выборки, рёбра — где грани сходятся под углом больше 25°.
- Режимы (`view/model.rs`): «Изменения» — новая версия прозрачной (рентген) или серой, добавленное зелёным, убранное красным; «Было» — старая версия и убранное; «Стало» — новая версия и добавленное. Цветные места рисуются поверх совпадающих серых граней без ряби.
- Долгая работа (чтение версий, сравнение) идёт в фоновых потоках (`app/jobs.rs`); окно не замирает и показывает ход работы.

### Проверки

- `nonius-scene` и `nonius-app`: обычные тесты без окна (сцена ↔ glTF, кэш и его миграции, действия на временном проекте).
- `nonius-gui`: тесты интерфейса без экрана ([egui_kittest](https://crates.io/crates/egui_kittest), `tests/window.rs` — весь путь от списка деталей до мест изменений на поддельном проекте) и проверка 3D-отрисовки в память (`tests/render.rs`: цвета режимов по пикселям). Отрисовка берёт любую видеокарту, в том числе программную (Mesa lavapipe в Linux, WARP в Windows); где её нет совсем, тест пропускается с пояснением.
- Ручная проверка на ПК Владимира перед мержем.

### Ограничения версий

## Разбор папки (`nonius-app/src/intake`)

Цель — снять с инженера раскладывание файлов. Он показывает папку, где модели, чертежи и бумаги лежат вперемешку; Nonius отвечает планом, человек смотрит и подтверждает.

```
 папка с файлами ──► intake_plan ──► IntakePlan (данные, ничего не изменено)
                        │                │  детали, сборки, версии, чертежи,
   LinkSource ──────────┘                │  у каждого решения — «почему»
   (SolidWorks: сборка → детали,         ▼
    чертёж → модель)              человек / окно / ИИ: посмотреть, поправить
                                         ▼
                                   intake_apply ──► копии в проект + версии в истории
```

Правила (в порядке силы):
1. Одно имя с разными расширениями — одна деталь: `вал.sldprt`, `вал.step`, `вал.pdf`.
2. Чертёж идёт к модели, на которую ссылается (отвечает SolidWorks), даже если назван иначе.
3. `вал`, `вал_v2`, `вал (3)`, `вал доработанный` — версии одной детали. Число без пометки версией не считается: `ЗАГЛУШКА12` — двенадцатая заглушка. Два файла из одной сборки — всегда разные детали.
4. Если в папке несколько сборок, у каждой своя папка, и детали, нужные только ей, лежат там же. Деталь из нескольких сборок остаётся снаружи.
5. Имя, занятое в проекте, не трогается: файлы остаются на месте, и об этом сказано.

Принципы:
- **Сначала план, потом действие.** `intake_plan` ничего не меняет. Догадки по именам помечены (`guessed`), чтобы человеку показали именно их.
- **Исходная папка не меняется.** В проект идут копии.
- **Работает без SolidWorks и без ИИ** — тогда только по именам. Связи от SolidWorks и подсказки ИИ лишь уточняют план.
- **План — данные** (`--json`): его одинаково читают окно, команда и ИИ. Будущий аддин SolidWorks, который сам сохраняет файлы в структуру проекта, может задать тот же вопрос про один файл и сообщать связи через ту же точку `LinkSource`.
- Файлы «не наши» (расчёты, логи, программы для станка) считаются числом, а не списком: в рабочей папке их сотни.

Что ещё не умеет: сравнивать геометрию, чтобы подтвердить «это версии одной детали»; спрашивать человека по одному вопросу (сейчас только пометка); раскладывать в уже существующие детали как новые версии.

## Задумано: сравнение в отдельном процессе

Не сделано, записано на будущее (замечание №6 проверки геометрии).

**Зачем.** Сейчас OpenCascade работает внутри программы. Отсюда три беды:
- если OpenCascade упадёт на кривом файле (такое бывает: это сбой в чужом коде на C++, Rust его не ловит), закроется всё окно вместе с несохранённой работой;
- «Остановить» срабатывает только между шагами: одну долгую булеву операцию прервать нельзя, поток досчитывает её впустую;
- OpenCascade не терпит двух чтений STEP сразу, поэтому сравнения идут строго по одному.

**Как.** Тот же `nonius.exe` запускается вторым процессом со скрытой командой-работником (например `nonius worker`): получает задание «сравни эти два файла с таким допуском, результат положи в эту папку», пишет ход строками в вывод и кладёт отчёт и `changes.glb` в папку кэша. Главная программа читает ход, а при «Остановить» просто завершает процесс — мгновенно.

- Упал работник — окно живо и говорит: «Сравнение не удалось: геометрическое ядро не справилось с файлом».
- Несколько сравнений могут идти одновременно: у каждого процесса свой OpenCascade.
- Обмен — через файлы кэша, которые уже есть (`cache.yaml`, `changes.glb`): нового формата не нужно. Задание и ход — JSON построчно; тот же разговор пригодится для модулей «внешний процесс по JSON-RPC».
- Место в коде: запуск работника — в `nonius-app` (рядом с `compare.rs`), команда — в `nonius-cli`; модули `nonius-occt` не меняются. Память о последней разнице на потоке (`shared_diff`) остаётся внутри работника.
- Цена: запуск процесса и чтение STEP заново — доли секунды, прочитанные STEP уже кэшируются (`nonius-occt/src/cache.rs`).

Так же стоит запускать превью и чтение паспорта при импорте: это тот же OpenCascade на незнакомом файле.
