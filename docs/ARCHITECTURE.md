# Архитектура Nonius

Ядро на Rust связывает CAD, людей и ИИ через одну папку проекта. Источники только поставляют файлы; хранение, сравнение и заметки — в ядре и модулях; интерфейс общается с ядром через локальный API.

```
 Аддин SolidWorks      Любой CAD            ИИ-агенты
 (C#: STEP, SLDPRT,    (Компас, Fusion,     (MCP, API, CLI)
  дерево)               FreeCAD: STEP)
        │                    │                    ▲▼
        ▼                    ▼                    │
 ┌─────────────────── Программа на Rust ───────────────────┐
 │  Хранилище версий          │  Сравнение                 │
 │  git + LFS, файлы/ссылки   │  OpenCascade через FFI     │
 │  история, варианты, откат  │  числа, подсветка, дерево  │
 │────────────────────────────┼────────────────────────────│
 │  Заметки и ссылки          │  API и MCP                 │
 │  Markdown, [[ссылки]]      │  синхронизация с сервером  │
 └──────────────────────────────────────────────────────────┘
        ▲▼                   │                    ▲▼
 Папка проекта          Окно программы       Сервер проекта
 STEP, YAML, Markdown   (egui, в nonius.exe) Forgejo: роли, блокировки
```

Какой файл за что отвечает — в [CODEMAP.md](CODEMAP.md).

## Папка проекта

```
мой-проект/
├── project.yaml            # имя, участники, роли, допуски сравнения
├── AGENTS.md               # описание проекта и правила для ИИ
├── .gitattributes          # бинарные файлы CAD через Git LFS
├── Стена/                  # папка-группа: обычная папка, уровней сколько угодно
│   ├── .gitkeep            # держит в git пустую папку
│   └── PANEL-00/           # деталь или сборка — папка с meta.yaml
│       ├── meta.yaml       # вид (деталь/сборка), масса, объём, габариты, материал, свойства
│       ├── tree.yaml       # дерево построения (если из SolidWorks)
│       ├── model.step      # геометрия, есть всегда
│       ├── model.sldprt    # исходник
│       ├── preview.png
│       └── docs/           # чертежи, PDF, DXF
├── RAIL-01/                # деталь может лежать и прямо в корне
└── notes/                  # заметки Markdown со ссылками [[деталь@v3#Фича]]
```

Дерево проекта — это папки на диске, один к одному (как хранилище Obsidian). Отдельного списка «какая деталь где» нет: деталь — любая папка с `meta.yaml`, внутрь детали обход не заходит, остальные папки — группы (`nonius_core::project::layout`). Вид детали берётся из её `meta.yaml`. Имя детали уникально во всём проекте: это её имя в истории (`Nonius-Item`), а место может меняться. Карту для программ и ИИ даёт `nonius map --json`.

До `project.yaml` схемы 2 детали лежали в `parts/<имя>/`, сборки — в `assemblies/<имя>/`. Такой проект открывается только для просмотра (`Project::writable` → код `old_layout`), окно один раз спрашивает «Обновить?», команда — `nonius upgrade`. Обновление (`Store::upgrade`) — одна запись истории: `git mv` каждой детали в корень (несохранённое переезжает и остаётся несохранённым), `project.yaml` схемы 2 и строка `Nonius-Layout: 2`. Если что-то не получилось (папка с таким именем уже есть, файл занят), всё возвращается как было.

Каждый файл данных начинается с `schema: N` (`nonius_core::schema`). Программа читает свою и более старые схемы (через миграции) и отказывается читать более новые, чтобы не испортить файл.

## Ядро и модули

Ядро (`nonius-core`) — только формат проекта, схемы, имена, точки расширения и реестр. Всё остальное — модули, и встроенные подключаются так же, как сторонние.

| Точка (`ExtensionPoint`) | Трейт | Что делает | Примеры |
|---|---|---|---|
| `GeometrySource` | `GeometrySource` | файл → паспорт версии (`meta.yaml`) | STEP через OpenCascade, SLDPRT без SolidWorks |
| `TreeSource` | `TreeSource` | файл → дерево построения | аддин SolidWorks, FreeCAD |
| `Comparator` | `Comparator` | различия двух версий; `quick()` — «отвечаю за доли секунды», такие сравнения зовёт разбор папки; обещание проверяет `contract::comparator` (на образцах — не дольше 5 с) | паспорт (встроен: `meta-compare`), геометрия, дерево, BOM |
| `Renderer` | `Renderer` | картинки и GIF изменений (`render_with` получает допуск проекта) | цветная подсветка |
| `Exporter` | `Exporter` | файлы из версии | DXF, PDF, STL |
| `Converter` | `Converter` | файл CAD → STEP при импорте; `stamp` — от чего, кроме самого файла, зависит STEP (ключ склада STEP); `to_step_asked` — то же с пожеланиями просящего (`ConvertAsk`: срочно ли, строка хода, отмена); окончательный отказ — `Error::Refused` | SolidWorks (встроен: `solidworks-step`) |
| `Links` | `LinkSource` | связи файлов: сборка → детали, чертёж → модель | SolidWorks (встроен: `solidworks-links`), позже аддин |
| `Glance` | `ShapeGlance` | беглый взгляд на форму прямо из файла CAD: объём, площадь, габариты, грани — приблизительно, зато без CAD-системы. Исходов три: строгий ответ (`glance`), отказ и «прочитано частично, вот что не прочитано» (`glance_partial`) | `.sldprt` (встроен: `sldprt-glance`) |
| `Design` | `DesignSource` | замысел конструктора прямо из файла CAD: операции с постоянными идентификаторами и размерами, конфигурации, материал, свойства, признаки «спорной» детали; ответ бывает неполным | SolidWorks (встроен: `sldprt-design`) |
| `Events` | `EventHandler` | реакция на события | уведомления в Telegram, проверки перед утверждением |
| `Ui` | — | панели интерфейса | подключаются веб-интерфейсом |

Правила, чтобы модули ничего не ломали:
- у модуля `ModuleManifest`: id, название, версия, версия API, точки, права;
- реестр подключает модуль только к точкам из манифеста и проверяет версию API (`API_VERSION`, `MIN_API_VERSION`);
- права явные (`Permission`);
- для каждой точки есть контрактная проверка в `nonius_core::contract`; модуль, прошедший её, совместим;
- ядро не знает о конкретных модулях; отключение модуля не теряет данные — они в открытых форматах.

Способы подключения: встроенный крейт (сейчас), внешний процесс по JSON-RPC и WASM-модуль (позже).

**Третий исход чтения** (`nonius_core::design::Partial`). Чтение чужого файла не обязано быть «всё или ошибка»: модуль отдаёт то, что прочитал, и список пропусков (`Gap`: постоянный код и слова для человека). Так отвечают `DesignSource::read_design` и `ShapeGlance::glance_partial`. Строгий `ShapeGlance::glance` остался как был — числам из него верят без проверки, и разбор папки зовёт именно его; `glance_partial` добавлен методом с ответом по умолчанию, поэтому прежние модули и вызывающие не меняются. Контракт проверяет согласие: строгий ответил — в неполном те же числа; строгий отказал, а неполный отвечает — причина записана пропуском.

**Почему замысел — отдельная точка, а не `TreeSource`.** `TreeSource` обещает дерево построения, как его знает сама CAD-система (аддин): порядок дерева, погашение, точные значения с единицами — и пишется в `tree.yaml`, схему которого нельзя менять без миграции. Чтение файла как есть обещать этого не может: операции в файле отсортированы, а не идут по дереву, погашение не записано, размеры — как показаны на экране. Зато в файле лежит то, чего в дереве нет: свойства, сохранённая масса, признаки «спорной» детали. Вместить это в `FeatureTree` значило бы добавить в схему файла пометки «неизвестно»; отдельная точка `Design` с собственными данными (`nonius_core::design::Design`, в файлы проекта не пишется) обходится без миграций и не выдаёт приблизительное за точное. Когда появится аддин, обе точки смогут работать рядом: дерево — от аддина, замысел — из файла, когда SolidWorks не запущен.

**Сравнение замыслов** (`nonius_core::design::diff`). Два замысла сравниваются по постоянным идентификаторам операций: добавлена, удалена, переименована, изменился размер (`Change`). Переименование не выглядит как «удалили и добавили», перестановка в списке изменением не считается, служебные узлы (папки, свет) помечены, чтобы их можно было отбросить. Это только данные: слова для человека и показ в окне — дело следующих шагов. Сравнение пока никем не вызывается — точка `Comparator` работает со `Snapshot`, а замысел в версию ещё не сохраняется.

### Форма прямо из файла SolidWorks (`nonius-sldprt`)

Файл `.sldprt` — по сути zip-архив со спрятанными сигнатурами и именами (`container/`): список секций берётся из центрального каталога в конце файла, каждая секция распаковывается один раз и только когда нужна, а распаковка ограничена пределом, который растёт с размером файла (чужой файл не займёт память сверх разумного). У обрезанного файла каталога нет — тогда секции ищутся по меткам и принимаются только с верной контрольной суммой. Старый контейнер OLE не читается и называется прямо. Среди них `Contents/DisplayLists` — сетка, которой SolidWorks рисует деталь: на каждую грань ленты треугольников с нормалями. По ней модуль `sldprt-glance` (точка `ShapeGlance`) считает объём, площадь, габариты и число граней за миллисекунды, не запуская SolidWorks; объём поправляется по нормалям, чтобы круглое не «худело» от огранки. Модуль отказывается, а не гадает, если сетки нет, она не замкнута или старее модели (метка `…/DLUpdateStamp` не равна метке в `ModelStamps`), а также если деталь — производная от другой (в манифесте операция `Stock`): в сетке таких деталей лежат лишние тела, и числа расходились с SolidWorks на десятки процентов. Там, где числа всё же сняты (сетка не замкнута — габариты и площадь верны; деталь производная), их отдаёт `glance_partial` с перечнем оговорок. Там же лежит готовая картинка `PreviewPNG` — её отдаёт `nonius_sldprt::preview_png` (в окно пока не подключена). Формат разобран по настоящим файлам и нигде не описан официально: подробности — в `//!` файлов `container/mod.rs` и `mesh.rs` и в базе знаний [docs/formats/](formats/README.md) (там же — что ещё лежит в файле: точная форма Parasolid, дерево построения с размерами, состав сборки, сохранённая масса).

**Замысел из файла** (`nonius-sldprt/src/design/`). В том же файле обычным XML лежит то, что конструктор задумал: список операций с постоянными номерами и размерами (`swXmlContents/KeyWords`), конфигурации и ссылки на другие файлы (`swXmlContents/Features`), состав сборки (`swXmlContents/COMPINSTANCETREE`), свойства — масса, материал, графы ЕСКД (`docProps/*.xml`), модель чертежа (свойство `SW-Config-Model-View-Sheet-List`). `Design::open` читает это за миллисекунды. Чтение не бывает «всё или ничего»: рядом с прочитанным — список `gaps`, что не прочитано и почему. `Design::doubts` одной функцией называет причины не верить сохранённому («спорная» деталь): не перестроена, производная от другой, зависит от других файлов, импорт, таблица параметров, несколько конфигураций, старая версия. Ядру это отдаёт модуль `sldprt-design` (точка `DesignSource`). Чего в XML нет: порядка дерева (в файле операции отсортированы), погашения, точных значений размеров (записано показанное на экране), уравнений, эскизов. Личные данные (`SW-Last Saved By`) из файла не читаются вовсе.

### Файл SolidWorks без ручного STEP (`nonius-solidworks`)

`.sldprt` — закрытый формат: Nonius хранит его как есть, а форму, массу и сравнение считает по STEP. Чтобы человек не выгружал STEP руками при каждом импорте, есть точка `Converter`: при импорте `.sldprt` / `.sldasm` модуль получает STEP, и импорт кладёт его рядом как `model.step` — дальше всё идёт обычной дорогой STEP (паспорт, превью, сравнение).

SolidWorks зовётся редко — для точной формы спорных деталей, слов «что изменилось» и точной 3D-подсветки; всё остальное Nonius читает из файла сам (`nonius-sldprt`). Поэтому связка устроена так, чтобы не мешать человеку и не ждать зря:

```
 импорт, разбор папки, «Показать в 3D»
   └─ nonius-app import.rs::convert
        ├─ склад STEP (.git/nonius/steps): тот же файл при тех же условиях — STEP сразу, SolidWorks не нужен
        └─ Converter::to_step_asked ──► nonius-solidworks
             hub.rs      одна очередь на программу: сначала то, чего ждёт человек; состояние наружу
             session.rs  надзор за командой: сроки, «умер», «занят», перезапуск, отказ после двух падений
             worker.rs   труба к рабочему процессу (строки UTF-8)
               └─ powershell worker.ps1 + helper.cs — один на всю работу программы
                    └─ СВОЙ SolidWorks: SLDWORKS.exe /r, объект из ROT по SolidWorks_PID_<pid>, Job Object
```

**Свой экземпляр.** К SolidWorks, открытому человеком, Nonius не подключается: трудная деталь может уронить SolidWorks, а там несохранённая работа. Рабочий процесс сам запускает `SLDWORKS.exe /r` без окна, берёт COM-объект именно этого процесса из таблицы запущенных объектов Windows (ROT) по имени `SolidWorks_PID_<pid>` (перебор таблицы; `GetActiveObject` и `New-Object -ComObject` отдали бы первый попавшийся SolidWorks — возможно, сеанс человека), ждёт `StartupProcessCompleted`, ставит `Visible = false`, `UserControl = false`. Свой процесс известен по номеру и времени старта (`nonius_solidworks::own`). Он живёт в группе процессов (Job Object с `KILL_ON_JOB_CLOSE`): не стало рабочего процесса — Windows закрывает и его; за самим Nonius следит нить рабочего процесса. Обычный конец работы вежливый (`ExitApp`); простоял две минуты — закрывается сам. Общие настройки человека не меняются: ни `SetUserPreference*`, ни параметры STEP, ни надстройки (`AddInsStartup`), ни OpenGL, ни `FrameState`. STEP пишется по настройкам человека; они только читаются из реестра — в ключ склада. Но сам SolidWorks, даже невидимый, пишет в реестр человека: открытые Nonius файлы попадают в его «последние документы», меняется раскладка панелей (проверено, см. `solidworks-automation.md` §8) — это не решено.

**Один рабочий процесс.** Раньше на каждую деталь запускался свой `powershell.exe`; теперь он один и читает команды построчно из stdin: `step <файл> <куда>`, `deps <файл>`, `ping`, `quit` — и отвечает `OK` / `ERROR <код> <причина>` (`wire.rs`; поля через табуляцию, UTF-8 мимо консоли: пути с кириллицей и пробелами). Разговор идёт через PowerShell и встроенный в него C# (`helper.cs`, компилирует сам PowerShell), а не из Rust: так не нужен `unsafe` (он запрещён в workspace) и нет новых зависимостей от Windows API.

**Надзор** (`session.rs`). У COM-вызова своего срока нет, поэтому срок считается в Rust по «пульсу» рабочего процесса (раз в секунду: время процессора своего SolidWorks и заголовок его окна-сообщения). Процессор стоит 90 с — завис; появилось окно отчёта об ошибке — упал; другое окно при стоящем процессоре — ждёт человека, которого нет; пока процессор занят — ждём, до 20 минут. Коды COM: `0x80010108`, `0x800706BA`, `0x80010007` — умер; `0x80010001`, `0x8001010A` — занят, команда повторяется без перезапуска. Упал или завис — рабочий процесс снимается (свой SolidWorks уходит следом), поднимается новый, команда повторяется; человек видит в строке хода «SolidWorks перезапускается». Файл, который уронил SolidWorks два раза подряд, получает окончательный отказ (`Error::Refused`) — он ложится на склад, и больше файл не пробуют, пока он не изменится. Каждые 50 выгрузок STEP — вежливый перезапуск: за долгую пачку SolidWorks копит память. Неудачный запуск минуту не повторяется: папка не ждёт по три минуты на деталь. Уже посчитанное не теряется: оно на складе и в памяти разбора. Срок по `docProps/OpenTime.xml` не используется: его единицы не выяснены.

**Очередь и состояние** (`hub.rs`). SolidWorks один и не распараллеливается. Очередь к нему одна, с двумя ступенями: сначала просьбы человека (импорт, «Показать в 3D», раскладка — `ConvertAsk::urgent`), потом фоновые (уточнение разбора, связи файлов). Идущую команду срочная просьба не прерывает. Состояние для индикатора в окне — `nonius_solidworks::status()`: `Missing` (не установлен) / `Idle` (свободен) / `Working { file, done, total }` (работаю над X, k из N) / `Restarting`; читать можно из любой нити, SolidWorks от этого не будится. Самого индикатора в окне пока нет.

**Склад STEP** (`nonius-app/src/steps.rs`). Ключ — SHA-256 содержимого файла и отпечаток условий перевода (`Converter::stamp`). Для SolidWorks (`stamp.rs`) это: установленный `SLDWORKS.exe` (путь, размер, время — меняются с обновлением), настройки STEP человека (`HKCU\Software\SolidWorks\SOLIDWORKS <год>\Export Settings`, только чтение), активная конфигурация (STEP пишется только с неё) и SHA-256 файлов, от которых зависит форма: у сборки — всех компонентов, у детали «в контексте» или производной — документов внешних ссылок. Список зависимостей берётся из самого файла (`nonius-sldprt`, `Design`); каждая ищется по записанному пути и в папке файла. Зависимость не нашлась или файл не читается (старый формат) — STEP на склад не кладётся: устаревшего STEP там быть не должно. На складе лежат готовые STEP, окончательные отказы («SolidWorks не справился») и пометка «тела нет» (STEP есть, а твёрдого тела в нём нет).

*Почему склад в `.git/nonius/` проекта, а не в общем кэше пользователя.* Он лежит рядом с памятью разбора (`intake-shapes.tsv`), строки `failed` которой на него опираются, и подчиняется тем же правилам: это кэш проекта, его можно удалить, он не попадает в историю, уходит вместе с проектом и переезжает с черновиком. У программы не появляется общего для всех проектов состояния на компьютере, а тесты изолированы сами собой. Цена — один и тот же файл в двух проектах выгружается дважды; для рабочего потока (разобрать папку → посмотреть в 3D → разложить в тот же проект) это не важно. Предел — 512 МБ на проект (`NONIUS_STEP_STORE_MB`): при переполнении удаляются самые давно не нужные записи, пока не останется три четверти; очистка целиком — `App::forget_steps` или просто удалить папку `.git/nonius/steps`.

- Модули `solidworks-step` и `solidworks-links` подключаются, только если SolidWorks установлен (запись `SldWorks.Application` в реестре Windows). Нет SolidWorks — импорт работает как раньше и предупреждает, что STEP прежний.
- Перевод не удался — это предупреждение, а не ошибка: файл всё равно импортируется.
- Команда `nonius import` — отдельный запуск программы: свой SolidWorks поднимается на каждый запуск (5–20 с) и закрывается с ним. Пачку файлов быстрее вести одной командой (`nonius intake`) или из окна.
- Время на этой машине (SolidWorks 2025 SP5): запуск своего экземпляра 5–8 с, первая выгрузка после запуска около 7 с (SolidWorks догружает модуль STEP), дальше 1–1,5 с на деталь в 150 КБ.
- Две найденные на практике ловушки записаны в скрипте: короткая запись вызовов PowerShell ломается на битом описании типов SolidWorks (поэтому `InvokeMember`), а деталь, открытая без окна в невидимом SolidWorks, роняет его модуль выгрузки STEP (поэтому деталь открывается с окном).
- Что ещё известно о SolidWorks по COM и что проверено на этой машине — [docs/formats/solidworks-automation.md](formats/solidworks-automation.md).

## Хранилище версий (`nonius-store`)

Версия детали — коммит git, который меняет только папку этой детали. В сообщении — описание и служебные строки:

```text
кронштейн v3: толщина 4 → 5 мм под новый вал

Nonius-Item: кронштейн
Nonius-Version: v3
```

- номер версии у каждой детали свой и растёт на 1;
- бинарные файлы идут через Git LFS по `.gitattributes`, файлы версии читаются `git cat-file --filters`;
- откат (`restore`) создаёт новую версию с содержимым старой — история не переписывается;
- удаление и переименование детали — отметки в истории (`Nonius-Deleted`, `Nonius-Renamed`, `Nonius-Recovered`), а не версии: удалённая деталь возвращается, версии идут за деталью через переименования, новая деталь со старым именем чужих версий не получает;
- перенос детали в другую папку — отметка `Nonius-Moved: <прежний путь>`; у удалённой детали `Nonius-Folder` — где она лежала, туда она и возвращается. Папку каждой версии `lineage.rs` прослеживает назад по этим отметкам, переименованиям и записи `Nonius-Layout` (до неё — `parts/<имя>` или `assemblies/<имя>`), поэтому старые версии читаются после любых переносов, а история не переписывается;
- используется системный `git`, а не библиотека: он уже умеет LFS и ведёт себя одинаково у всех.

## Действия программы (`nonius-app`)

Командная строка, окно и (позже) MCP вызывают одни и те же действия `nonius-app::App`: детали со статусом, история, сохранить версию, откат, выгрузка, импорт, паспорт, сравнение. `nonius-app` ничего не печатает и не знает о конкретных модулях: реестр собирает вызывающий. `App` можно делить между потоками — окно вызывает долгие действия в фоне, передавая `Progress` (шаги и отмена).

**Масса** = объём × плотность и считается только при заданном материале. Материал и плотность (`density_kg_m3`) лежат в `meta.yaml` и попадают в версию. Плотность берётся из справочника частых материалов или вводится вручную; «по умолчанию» не подставляется. Без материала программа так и пишет: масса не посчитана.

**Кэш сравнений** — `.git/nonius/cache/<ключ>/`, в историю не попадает. Ключ — хеш обеих версий (коммит; для текущего состояния — пути, размеры и время изменения файлов), допусков и версий модулей. Хранятся 200 последних записей, старые удаляются — кэш всегда можно пересчитать. Отчёты и файлы отрисовщиков (`changes.png`, `changes.glb`) кэшируются отдельно. Описание записи `cache.yaml` начинается с `schema: N` и меняется только с миграцией; незнакомая, битая или неполная запись пересчитывается. Запись готовится во временной папке и ставится на место одним переименованием (`nonius_store::workdir`, так же выкладываются версии).

## Цвета подсветки

`ChangeKind` в отчёте сравнения привязан к цвету: `Added` — зелёный, `Removed` — красный, `Moved` — жёлтый, без изменений — приглушённый.

## Окно программы (`nonius-gui`)

Двойной щелчок по `nonius.exe` (или `nonius view [деталь] [было] [стало]`) открывает окно: детали проекта, выбор версий «Было» и «Стало», деталь в 3D с цветной подсветкой изменений, список мест изменений, числа из паспортов. Окно — часть того же exe, без браузера, ничего не нужно ставить. Командная строка работает как прежде; `NONIUS_NO_WINDOW=1` вместо окна печатает подсказку (серверы, проверки).

Окно получает проект через трейт `nonius_gui::source::ProjectSource`; реализация поверх `nonius-app` лежит в `nonius-cli/src/window/source/` (`AppSource`). Поэтому окно и команды берут сравнения из одного кэша. Для окна реестр собирается без картинки `changes.png` (`nonius_occt::register_for_window`): ему нужна только сцена. Сравнения идут по одному: OpenCascade не терпит параллельного чтения STEP. Долгое сравнение можно отменить: окно сразу свободно, расчёт бросается между шагами; шаг, который успел досчитаться, остаётся в кэше — второй раз он не считается. В окне же — история детали, сохранение версии с обязательным описанием, материал (справочник или своя плотность) и масса «было → стало»; всё это — те же действия `nonius-app`, что у команд `commit` и `material`.

### Вкладки проектов и черновик

Проекты открываются вкладками, как в браузере. Всё, что окно знает об одном проекте (детали, версии, сравнение, окошки), лежит в `ProjectTab`; у каждой вкладки своя очередь фоновых работ, поэтому результат не попадает в чужую вкладку. Рисуется только открытая вкладка, остальные ждут. Один проект в одном окне: замок `.git/nonius/window.lock` (`nonius-cli/src/window_lock.rs`) не даёт открыть его во втором окне, а в этом окне повторное открытие просто переходит к его вкладке.

Папка для начала работы не нужна. «Новый проект» (и запуск без открытых вкладок) создаёт черновик — обычный проект Nonius с git, только во временной папке программы `%LOCALAPPDATA%\Nonius\drafts\<метка>\Без имени`. Второй системы хранения нет: черновик отличается от проекта лишь местом на диске. «Сохранить проект как…» переносит папку целиком, с историей, в выбранную пустую папку (`nonius_app::move_project`): на том же диске — переименование, на другом — копия и удаление; название проекта становится именем папки. Перенос ждёт, пока закончатся все потоки вкладки, даже отменённые: они держат файлы проекта открытыми. Закрыть вкладку или окно с несохранённым черновиком, где есть детали, можно только после вопроса; «Не сохранять» отправляет черновик в Корзину (правило «ничего не удаляется»), пустой черновик стирается.

Проект старого формата (`parts/`, `assemblies/`) окно открывает только для просмотра: при открытии один раз спрашивает «Обновить?» («Не сейчас» / «Обновить»), дальше над проектом остаётся жёлтая полоса с той же кнопкой (`app/upgrade.rs`). Обновление ждёт, пока вкладка свободна, и открывает проект заново.

### Выделение → команда → очередь

Дерево и «Структура» называют предметы одним словом — `Node` (деталь, папка, файл папки) — и делят одно выделение (`app/selection.rs`): отмеченное в одном виде подсвечено и в другом. Клавиша, пункт меню и перетаскивание не делают работу сами, а просят одну команду (`app/command.rs`: удалить, перенести, выделить всё, снять выделение, переименовать, открыть); что она значит для одного предмета и для нескольких, решается там же. Клавиши выделенного (Delete, Ctrl+A, Esc, F2, Enter) слушаются в конце кадра и только когда ни один виджет не держит клавиатуру, не открыто окошко и не открыто меню. В окошке с кнопками главная кнопка сразу в фокусе и ←/→ выбирают соседнюю; в открытом меню ↑/↓ ходят по пунктам по кругу (`app/choice.rs`: стрелки окно забирает раньше egui, иначе egui двигает фокус на два пункта и за край меню). Несколько предметов идут очередью (`app/batch.rs`): одна фоновая работа, предметы по одному, ход «Переношу 3 из 5: …» и «Остановить» (после текущего) в строке состояния; итог — одной строкой, ошибки — по строке на предмет. Очередь не отменяется выбором другой детали, а запись в проект и так идёт по очереди (`writing()` в `nonius-cli/src/window/source`). У очереди своя строка хода: сравнение рядом и его отмена её не стирают. Сбой (паника) в предмете очереди не оставляет её «занятой»: очередь останавливается и присылает итог. Сбой любой другой работы (`Done::Crashed`) снимает ожидание со всего, что ждёт результата (`ProjectTab::stop_waiting`); закрытие вкладки или другой проект в ней останавливают очередь (`ProjectTab::abandon`).

Окно получает эти действия так же, как открытие и создание проекта, — замыканиями в `nonius_gui::Options` (`opener`, `creator`, `mover`, `discard`): `nonius-gui` не знает про git, файловые операции и Корзину.

Окно помнит открытые вкладки и переключатели вида в `%APPDATA%\Nonius\window.txt` (Linux — `~/.config/nonius/window.txt`): строки `tab=<папка>` по порядку и `active=<номер>`; строка `last_project` из прежних версий читается как вкладка. Испорченный файл не мешает запуску, пропавшие папки пропускаются.

### Крейты и границы

```
 nonius-cli (exe) ──┬── nonius-gui ──┐       окно: egui + wgpu
   команды,         │                ├── nonius-app     действия программы
   сборка реестра   └────────────────┘        │
   модулей                                    ├── nonius-store   версии: git + LFS
                                              ├── nonius-scene   модель сцены и glTF
                                              └── nonius-core    формат, схемы, точки расширения
 модули: nonius-occt (OpenCascade), nonius-step, nonius-solidworks, nonius-sldprt … — подключаются к реестру из nonius-core
```

| Крейт | Что внутри | Чего не знает |
|---|---|---|
| `nonius-core` | формат проекта, схемы, точки расширения, реестр | окна, git, OpenCascade |
| `nonius-scene` | модель сцены: слои, сетки, места изменений, подписи; запись и чтение glTF (`.glb`) | OpenCascade, egui, git |
| `nonius-app` | **действия**: открыть проект, детали, история, сравнить (с кэшем и в фоне), импортировать модель, сохранить версию, откатить, выгрузить, задать материал | окна и консоли |
| `nonius-gui` | окно: панели, 3D-вид, мышь, фоновые задачи, тексты интерфейса | OpenCascade и git: всё через `nonius-app` |
| `nonius-cli` | разбор команд и печать; собирает реестр со встроенными модулями и передаёт его в `nonius-app`; без команды открывает окно | — |

Правила:
- CLI, окно, а позже MCP и сервер вызывают **одни и те же действия** `nonius-app`. Логика не дублируется: что умеет окно, умеет и команда, и ИИ.
- `nonius-core` не тянет графику: в ядре нет egui, wgpu и glTF.
- Отрисовщик (`Renderer`) отдаёт сцену файлом `changes.glb`. Окно читает его через `nonius-scene` и не знает, каким модулем и из какого CAD-формата он сделан. Сменить движок отрисовки окна или добавить новый формат — работа одного крейта.
- Будущие панели модулей (калькулятор массы, раскрой листа) подключаются к точке `Ui` через трейт панели в `nonius-gui`. Трейт появится вместе с первым таким модулем.

### Модель сцены (`nonius-scene`)

Сцена — то, что показывается в 3D:
- **место** — кусок материала с ролью, сеткой и объёмом. Роли: `after` (новая версия целиком, «стало»), `before` (старая версия целиком, «было»), `added`, `removed`, позже `moved`. Каждый отдельный кусок добавленного или убранного материала — своё место: по списку мест окно приближает к изменению;
- цвет роли один для картинок, 3D и интерфейса (`Role::color`);
- сетки в мм, оси — как в исходном файле (у SolidWorks Y вверх).

На диске сцена хранится в стандартном glTF 2.0 (`.glb`): узел на каждое место, роль и объём лежат в `extras`. Старая версия целиком лежит во второй сцене glTF, поэтому сторонние программы (Средство 3D-просмотра Windows, Blender) показывают «стало» с цветными изменениями.

**Формат сцены и формат кэша — публичный контракт с номером версии**, как схемы файлов проекта:
- в `asset.extras.nonius_scene` у `.glb` записан номер формата сцены; в `cache.yaml` — `schema: N`;
- новые поля добавляются так, чтобы старые программы их пропускали; несовместимое изменение повышает номер и идёт с миграцией и тестом на старый файл;
- более новый формат программа не читает и объясняет, что пора обновиться;
- `nonius_scene::contract` проверяет сцену любого модуля-отрисовщика (роли, сетки, единицы, номер формата). Её прогоняют тесты `nonius-scene` без OpenCascade и тесты каждого отрисовщика; в репозитории лежит образец `.glb` каждой версии формата, и новые программы обязаны его читать.

### Поток данных при сравнении

```
окно: выбрали «было» и «стало»
  → nonius-app: ключ кэша = хеш обоих model.step + версии модулей
      ├─ есть в кэше → сразу отчёт и сцена
      └─ нет → фоновая задача с ходом выполнения и отменой:
            реестр: сравнения (отчёт) ‖ отрисовщик сцены (changes.glb)
            → записать в кэш
  → окно: 3D, места изменений, числа
```

Правила честности сравнения формы (`nonius-occt/src/modules/diff.rs`):

- **Шум — по толщине куска, а не по доле объёма детали.** Булевы операции оставляют плёнки вдоль совпадающих граней; плёнка тоньше допуска проекта — шум. Толщина куска = объём / половина площади. Раньше шумом считалось всё меньше миллионной доли объёма детали, и в большой детали пропадало настоящее маленькое отверстие.
- **Один допуск на отчёт, картинку и сцену.** Программа зовёт отрисовщики через `Renderer::render_with` с допуском проекта, поэтому булева разница считается один раз и рисунок совпадает с числами.
- **Проверка баланса на всех трёх путях** (местная разница → тела целиком → два вычитания): «было + добавлено − убрано = стало». Не сошлось и на последнем — разница показывается со строкой «Сравнение формы приблизительное».
- **Нет твёрдых тел — так и сказано.** Файл из одних поверхностей даёт строку «Форма не сравнена», а не пустой отчёт.
- **Отказ запоминается** так же, как удача: сцена и картинка не повторяют за сравнением тот же долгий расчёт с тем же концом.

Кэш лежит в `.git/nonius/cache/` и в историю не попадает. Описание кэша `cache.yaml` начинается с `schema: N` и меняется только с миграцией, как все схемы. Незнакомую или битую запись программа пересчитывает и ничего не теряет.

### Тексты интерфейса

Все надписи окна собраны в одном модуле `crates/nonius-gui/src/texts.rs`: таблица строк, русский по умолчанию. Код окна берёт надписи только оттуда. Перевод на другой язык — ещё одна такая таблица; если языков станет много, таблица переедет в файлы готового формата (Fluent), а код окна при этом не поменяется. Сторонняя библиотека переводов сейчас не нужна: лишние зависимости в одном exe ни к чему.

### Мышь и клавиши — как в SolidWorks

| Действие | Мышь | Клавиши |
|---|---|---|
| вращать | средняя кнопка (или левая — для тачпада) | стрелки по 15°, Shift + стрелки по 90° |
| сдвигать | Ctrl + средняя | Ctrl + стрелки |
| поворот в плоскости экрана | — | Alt + ← → |
| приближать | колесо к курсору: от себя — отдалить (как в SolidWorks; есть «Колесо мыши наоборот»), Shift + средняя | — |
| показать целиком | двойной щелчок средней, кнопка «Целиком» | F |
| виды | кнопки над видом | Ctrl+1 спереди, 2 сзади, 3 слева, 4 справа, 5 сверху, 6 снизу, 7 изометрия |
| выбрать место изменения | щелчок левой по цвету или по строке списка (приближает) | — |

Сопоставление мыши и клавиш с движениями камеры — в `nonius-gui/src/view/controls.rs`, с тестами.

### Как устроен 3D-вид

- Камера ортогональная, как в CAD (`view/camera.rs`): виды, вращение вокруг центра детали, масштаб к курсору, «целиком», плавный переход между видами.
- Отрисовка (`view/gpu/`) идёт на видеокарте в отдельную картинку, которую окно показывает как изображение; та же отрисовка сохраняет PNG («Сохранить картинку») и работает в тестах без окна. Сглаживание краёв — 4 выборки, рёбра — где грани сходятся под углом больше 25°.
- Режимы (`view/model.rs`): «Изменения» — новая версия прозрачной (рентген) или серой, добавленное зелёным, убранное красным; «Было» — старая версия и убранное; «Стало» — новая версия и добавленное. Цветные места рисуются поверх совпадающих серых граней без ряби.
- Долгая работа (чтение версий, сравнение) идёт в фоновых потоках (`app/jobs.rs`); окно не замирает и показывает ход работы.

### Проверки

- `nonius-scene` и `nonius-app`: обычные тесты без окна (сцена ↔ glTF, кэш и его миграции, действия на временном проекте).
- `nonius-gui`: тесты интерфейса без экрана ([egui_kittest](https://crates.io/crates/egui_kittest), `tests/window.rs` — весь путь от списка деталей до мест изменений на поддельном проекте) и проверка 3D-отрисовки в память (`tests/render.rs`: цвета режимов по пикселям). Отрисовка берёт любую видеокарту, в том числе программную (Mesa lavapipe в Linux, WARP в Windows); где её нет совсем, тест пропускается с пояснением.
- Ручная проверка на ПК Владимира перед мержем.

## Разбор папки (`nonius-app/src/intake`)

Цель — снять с инженера раскладывание файлов. Он показывает папку, где модели, чертежи и бумаги лежат вперемешку; Nonius отвечает планом, человек смотрит и подтверждает.

```
 папка с файлами ──► intake_glance ──► IntakeStudy (беглое: секунды)
   форма бегло ──────────┘     │            │
   (ShapeGlance, готовый STEP) │            ▼  study.plan(ответы) — мгновенно
                               ▼     IntakePlan (данные, ничего не изменено):
                         intake_refine     детали, сборки, версии, чертежи,
   LinkSource ──────────────┤  │     у каждого решения — «почему», вопросы,
   (SolidWorks: сборка → детали,     спорное помечено (doubtful)
    чертёж → модель)        │  ▼            │        ▲
   точная форма спорных ────┘ IntakeStudy   ▼        │ ответ «да» / «нет»
   и слова (Converter)        (точное)   человек / окно / ИИ
                                                ▼
                                          intake_apply ──► копии в проект + версии в истории
```

`intake_study` — оба прохода подряд (так делает команда без `--fast`); окно показывает план после первого, а второй идёт в фоне.

Правила (в порядке силы):
1. Одно имя с разными расширениями — одна деталь: `вал.sldprt`, `вал.step`, `вал.pdf`.
2. Чертёж идёт к модели, на которую ссылается (отвечает SolidWorks), даже если назван иначе.
3. `вал`, `вал_v2`, `вал (3)`, `вал доработанный` — версии одной детали. Число без пометки версией не считается: `ЗАГЛУШКА12` — двенадцатая заглушка. Два файла из одной сборки — всегда разные детали. Догадку по именам проверяет форма деталей (ниже).
4. Одно имя в разных папках — копии проекта («рабочая версия», «готовая»). Файлы побайтно одинаковые — это одна деталь с одной версией. Отличаются — решает форма: одинаковая — тоже одна деталь (остаётся более новый файл), похожая — версии по времени файла, разная — разные детали (вторая получает имя папки в скобках). Формы нет — одному имени в разных папках не верим. Деталь ложится в папку своей последней версии.
5. Если в папке несколько сборок, у каждой своя папка, и детали, нужные только ей, лежат там же. Деталь из нескольких сборок остаётся снаружи.
6. Имя, занятое в проекте, не трогается: файлы остаются на месте, и об этом сказано.

Принципы:
- **Сначала план, потом действие.** `intake_plan` ничего не меняет. Догадки по именам помечены (`guessed`), а что о них сказала форма — в поле `shape`: человеку показывают то, что форма не подтвердила.
- **Исходная папка не меняется.** В проект идут копии.
- **Работает без SolidWorks и без ИИ** — тогда по именам и форме из самих файлов. Связи от SolidWorks, его точная форма и подсказки ИИ лишь уточняют план.
- **Сначала быстро, потом точно.** Первый проход (`intake_glance`) чужих программ не будит и даёт план за секунды; второй (`intake_refine`) спрашивает SolidWorks только о том, где беглого взгляда мало. Будить ли SolidWorks — настройка разбора: в окне галочка «Уточнять разбор папки через SolidWorks», в команде `--fast` («только быстро»).
- **План — данные** (`--json`): его одинаково читают окно, команда и ИИ. Будущий аддин SolidWorks, который сам сохраняет файлы в структуру проекта, может задать тот же вопрос про один файл и сообщать связи через ту же точку `LinkSource`.
- Файлы «не наши» (расчёты, логи, программы для станка) считаются числом, а не списком: в рабочей папке их сотни.

**Проверка формой** (`shape.rs`, `measure.rs`). Имя файла — слабое свидетельство, сама деталь — сильное. У каждой версии, угаданной по имени, снимается «отпечаток»: объём, площадь, три габарита (по возрастанию — поворот детали не мешает) и число граней. Источник формы явный (`shape::Source`): **беглая** — из самого файла CAD, точка `ShapeGlance`, модуль `nonius-sldprt` читает сетку показа, сохранённую в `.sldprt` (доли секунды, SolidWorks не нужен); **точная** — по STEP: готовый рядом, если он не старше файла CAD, или от SolidWorks через модуль перевода (секунды на деталь).

Проходов два (`measure.rs`). Первый (`Pass::Glance`) у каждой группы версий берёт беглую форму, а где её нет — готовый STEP; SolidWorks не зовёт. Группа **спорная**, если у какой-то версии формы нет или ответ сравнения на грани: при числах, сдвинутых на погрешность беглого взгляда (2 %) в одну и в другую сторону, ответ разный (`shape::doubtful`: «похожи ↔ разные», «копия ↔ версия»). Точные формы спорными не бывают. Спорные детали и вопросы помечены в плане (`doubtful`). Второй проход (`Pass::Exact`) снимает у спорных групп точную форму всех версий, теперь и через SolidWorks, а заодно спрашивает связи файлов и слова «что изменилось» для всех пар. STEP одной версии просят у SolidWorks один раз — и за проход, и между разборами: его помнит склад STEP на диске (`steps.rs`, см. «Файл SolidWorks без ручного STEP»); `exports::Exports` — только разрешение будить SolidWorks и сведения о том, кто просит. Уточнённая форма запоминается рядом с беглой; следующий разбор той же папки берёт точную сразу, если она помнится у всех версий группы.

Числа по сетке приблизительные: на 101 настоящей детали объём сошёлся с точным в пределах 2 %, а габариты — 1 % у 89; у 9 модуль отказался сам (нет сетки или она старее модели), 3 разошлись (резьба: объём −6 %; деталь, которую SolidWorks при открытии перестраивает в другую). Граней в сетке меньше, чем в STEP: там круглые грани разрезаны. Поэтому у версий одной группы источник по возможности один, а все поправки на беглую форму собраны в одном месте — `shape::Limits` (по двум источникам: с какого расхождения «копия», сравнимо ли число граней, на сколько ответ может ошибаться): точная против беглой — грани не сравниваются и «копией» считается расхождение до 2 %. В паспорт версии беглые числа не попадают. Промахи беглого взгляда, которые порог не ловит (деталь, которую SolidWorks при открытии перестраивает в другую: у обеих копий одинаково неверные числа), на ответ разбора пока не влияют: копия остаётся копией. Поймать такой промах по самому файлу честно нельзя: всё, что в файле лежит, согласовано между собой — и сетка (121 мм, 58 см³), и масса, которую SolidWorks сам записал при сохранении (`docProps/ISolidWorksInformation.xml`, 0,454 кг ≈ 58 см³ стали), и метки свежести сетки. Другой (86 мм, 35 см³) деталь становится, только когда SolidWorks перестраивает её при открытии, а это и есть точный путь. Признаки, которые проверены и не годятся: несколько несвязных кусков в сетке (в «шестерне» кусок один), метки `ModelStamps` / `DLUpdateStamp` (равны), STEP рядом (его нет).

Два отпечатка сравниваются так:

| Ответ | Когда | Что делает разбор |
|---|---|---|
| та же форма | все числа совпали | версии остаются, но сказано: «возможно, это копия» (`shape: copy`) |
| похожая | объём ушёл не дальше 25 %; габариты либо все в пределах 10 %, либо два из трёх те же (2 %) и третий в пределах 25 % | догадка подтверждена (`confirmed`), в «почему» — числа: «объём −0,8 %, габариты те же» |
| разная | остальное | детали расходятся: у каждой своё имя и строка «имя похоже на …, но форма другая» (`different`) |

Пороги подобраны по настоящим деталям: коллектор и его доработка (68×90×398 → 70×84×398 мм, объём +2,8 %) — версии. Глубина проверки — `ShapeCheck`: `Off` (только имена, мгновенно; `--quick`), `Names` (по умолчанию: только версии, угаданные по именам), `All` (`--deep`: форма всех деталей). В глубоком режиме разбор ещё и подсказывает про детали, которые по именам не связаны, а формой похожи или одинаковы («по форме похожа на …: возможно, это версии одной детали») — ничего не объединяя: решает человек. Детали из одной сборки в подсказки не попадают. Сборки формой не проверяются (перевод большой сборки в STEP — минуты). Правила проверки — чистые функции без диска; не удалось снять отпечаток — догадка просто остаётся непроверенной.

**Диалог** (`questions.rs`, `study.rs`). Там, где программа не уверена, она не решает молча, а кладёт в план вопрос (`IntakePlan.questions`): текст («Это версии одной детали: «вал» → «вал_v2»?»), улики (что сказала форма, когда файлы менялись) и своё мнение, если оно есть. Спрашивает о трёх вещах: версии угаданы по именам, а форма их не подтвердила; имена похожи, но форма разная (детали уже разведены — подтвердите); имена разные, а форма похожа (глубокий режим, и только когда пара одна — двадцать одинаковых заглушек остаются подсказкой). Ответ — `id` вопроса и «да»/«нет»: `study.plan(ответы)` пересчитывает план мгновенно, потому что долгая часть (диск, SolidWorks, форма) уже сделана при изучении. Слово человека сильнее и имён, и формы; в «почему» остаётся строка «вы ответили: …». `id` — имена файлов через `|`, от пересчёта не меняется: отвечать можно из консоли (`--ask`), заранее (`--yes ID`, `--no ID`), из окна и от ИИ. Мнение «похоже, нет» программа не высказывает, когда у «других» по форме деталей два габарита из трёх совпали (деталь могли укоротить или утолщить): в уликах стоит «два габарита из трёх совпали», а решает человек. Без ответов план выполняется как есть.

**Что изменилось — словами** (`words.rs`). Числа («объём −4 %») свою деталь узнать не помогают, слова — помогают. Для каждой пары соседних версий и для каждой пары из вопроса разбор спрашивает «быстрые» модули сравнения (`Comparator::quick`; сейчас это `features-occt`): «Новое отверстие ⌀8; Бобышка ⌀60, высота: 0.52 мм → 1.52 мм». Строка идёт в «почему» детали и первой уликой в вопрос. Модулям нужен STEP обеих версий — готовый (первый проход) или от модуля перевода (второй); посчитанное запоминается в `.git/nonius/intake-words.tsv`. Правила плана сами ничего не считают: они спрашивают готовое у `Words`, а недостающие пары изучение папки досчитывает один раз. В режиме `--quick` слов нет.

**Чему верить** (`split.rs`), от сильного к слабому: (1) две модели стоят в одной сборке — точно разные детали; (2) ответ человека; (3) форма; (4) имя — только внутри одной папки. Похожесть тянется по цепочке версий, но точно разные детали в одну не попадут.

**Скорость.** Копии ищутся без SolidWorks: у моделей одинакового размера снимается отпечаток содержимого (SHA-256). Форма, снятая с файла, запоминается в `.git/nonius/intake-shapes.tsv` по пути, размеру и времени файла (`memory.rs`; беглая помечена словом `mesh`, у версии могут быть обе записи; строка `failed` с причиной — точной формы не будет: SolidWorks выгрузил STEP, а тела в нём нет, как у пустой «Деталь1», или SolidWorks с деталью не справился (упал или завис два раза подряд, не открыл файл; сам отказ лежит на складе STEP). Такую версию не уточняют заново, пока файл не изменится; причина видна с `NONIUS_TRACE=1`). Папка ЧПУ-стола (155 файлов моделей): первый проход — 1,4 с; оба прохода с SolidWorks с нуля — около 4 минут (уточнено 27 версий спорных деталей, больше всего времени — слова «что изменилось»); повторно — 4 с. Замер 16.11.2026 на копии той же папки (отладочная сборка, SolidWorks 2025 SP5, уточняется 34 версии): с одним рабочим процессом и складом STEP оба прохода с нуля — 192 с вместо 223 с; повторный разбор — 11 с вместо 37 с; разбор, которому STEP нужны снова (память формы и слов стёрта, склад на месте), — 36 с вместо 224 с. Склад при этом занял 34 МБ. Больше всего времени первого прогона по-прежнему уходит не на SolidWorks, а на слова «что изменилось» (OpenCascade).

**В окне** (`nonius-gui/src/app/intake/`). «Файл → Разобрать папку…» — то же самое с кнопками. Окно не знает про `nonius-app`: четыре вызова `ProjectSource` — `intake_study` (быстрый проход, в фоне, со строкой хода; «Остановить» отдаёт план из того, что успели), `intake_refine` (точный проход, `refine.rs`: идёт сам после первого плана, если `IntakePlan.refine` и включена галочка «Уточнять разбор папки через SolidWorks» — она же в «Настройках», помнится в `window.txt`; спорные строки и вопрос помечены «уточняю…», на вопросы отвечать можно, «Разложить» ждёт; «Остановить» или снятая галочка — план остаётся беглым, так и сказано (после «Остановить» — «уточнение остановлено», при снятой галочке — «выключено»); уточнить можно снова кнопкой «Уточнить» или галочкой, посчитанное не пропадает), `intake_plan(ответы)` (мгновенный пересчёт после «Да», «Нет» и после уточнения) и `intake_apply(ответы)`. Тяжёлые работы с OpenCascade в одной вкладке идут по одной (очередь `busy` в мосте, `gate.rs`); пока работа ждёт SolidWorks (выгрузка STEP, связи файлов), она из этой очереди выходит (`Progress::outside`), и 3D-сравнение за выгрузкой STEP не стоит; если замок держит остановленное сравнение, которое доделывает булеву операцию, изучение, уточнение и раскладка пишут в строке хода «Жду, пока закончится прошлая работа…», а не молча стоят. Изученную папку (`IntakeStudy`) помнит мост `nonius-cli/src/window/source/intake.rs`, окно держит только ответы и показанный план. Вопросы идут по одному; «Потом» откладывает вопрос, раскладке это не мешает. После раскладки — итог (сколько разложено, предупреждения, что не вышло) и перечитанное дерево проекта.

**Показать в 3D** (`nonius-app/src/intake/look.rs`, окно — `nonius-gui/src/app/intake/sight.rs`). Слов о том, что изменилось, мало, чтобы узнать деталь, — у вопроса и у детали с версиями есть кнопка «Показать в 3D»: обе модели в том же 3D-виде, которым окно сравнивает версии детали (общее серым, убранное красным, добавленное зелёным), под картинкой — те же слова «что изменилось», что посчитал разбор (нет их — строки отчётов сравнения). Деталей ещё нет в проекте, поэтому сравниваются файлы с диска: `IntakeQuestion.sides` / `IntakeItem.sides` несут файлы каждой стороны (в ядре — `Question.versions` и `PlannedVersion.models`), слова — `changed`. `App::intake_compare` берёт STEP каждой стороны (`words.rs::step_of`: свежий рядом или от SolidWorks) и зовёт `App::compare_files` (`outside.rs`) — сравнение двух файлов, ни один из которых не деталь проекта. Кэш сравнений не трогается: копии и картинки — во временной папке (`FilesCompared` держит её, пока мост читает сцену). Не вышло нарисовать разницу (булева операция не сошлась) — отрисовщики рисуют каждую сторону отдельно, мост ставит их рядом (`Scene::beside`), а окно пишет «модели показаны рядом: слева …, справа …». Сравнение идёт в фоне со своей строкой хода и «Остановить» (STEP от SolidWorks — до минуты); у экрана свой 3D-вид (`App::intake_view`), модель и камера детали в главном виде не трогаются. Сбой фоновой работы (`ProjectTab::stop_waiting`) закрывает ждущий показ, закрытие вкладки (`abandon`) и экрана останавливает расчёт. Сборки не сравниваются: кнопки у них нет.

Что ещё не умеет: сворачивать копии сборок, если их пересохраняли (сборки формой не проверяются — склеиваются только побайтно одинаковые); замечать копию детали под другим именем без `--deep`; показывать слова для пар, которые появились после ответа человека (считаются только при изучении папки) (сейчас — по числам паспорта; точная сверка потребует новой точки расширения); объединять детали по подсказке глубокого режима; спрашивать человека по одному вопросу (сейчас только пометка); раскладывать в уже существующие детали как новые версии.
## Задумано: сравнение в отдельном процессе

Не сделано, записано на будущее (замечание №6 проверки геометрии).

**Зачем.** Сейчас OpenCascade работает внутри программы. Отсюда три беды:
- если OpenCascade упадёт на кривом файле (такое бывает: это сбой в чужом коде на C++, Rust его не ловит), закроется всё окно вместе с несохранённой работой;
- «Остановить» срабатывает только между шагами: одну долгую булеву операцию прервать нельзя, поток досчитывает её впустую;
- OpenCascade не терпит двух чтений STEP сразу, поэтому сравнения идут строго по одному.

**Как.** Тот же `nonius.exe` запускается вторым процессом со скрытой командой-работником (например `nonius worker`): получает задание «сравни эти два файла с таким допуском, результат положи в эту папку», пишет ход строками в вывод и кладёт отчёт и `changes.glb` в папку кэша. Главная программа читает ход, а при «Остановить» просто завершает процесс — мгновенно.

- Упал работник — окно живо и говорит: «Сравнение не удалось: геометрическое ядро не справилось с файлом».
- Несколько сравнений могут идти одновременно: у каждого процесса свой OpenCascade.
- Обмен — через файлы кэша, которые уже есть (`cache.yaml`, `changes.glb`): нового формата не нужно. Задание и ход — JSON построчно; тот же разговор пригодится для модулей «внешний процесс по JSON-RPC».
- Место в коде: запуск работника — в `nonius-app` (рядом с `compare.rs`), команда — в `nonius-cli`; модули `nonius-occt` не меняются. Память о последней разнице на потоке (`shared_diff`) остаётся внутри работника.
- Цена: запуск процесса и чтение STEP заново — доли секунды, прочитанные STEP уже кэшируются (`nonius-occt/src/cache.rs`).

Так же стоит запускать превью и чтение паспорта при импорте: это тот же OpenCascade на незнакомом файле.
