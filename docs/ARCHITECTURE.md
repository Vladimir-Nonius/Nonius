# Архитектура Nonius

Ядро на Rust связывает CAD, людей и ИИ через одну папку проекта. Источники только поставляют файлы; хранение, сравнение и заметки — в ядре и модулях; интерфейс общается с ядром через локальный API.

```
 Аддин SolidWorks      Любой CAD            ИИ-агенты
 (C#: STEP, SLDPRT,    (Компас, Fusion,     (MCP, API, CLI)
  дерево)               FreeCAD: STEP)
        │                    │                    ▲▼
        ▼                    ▼                    │
 ┌─────────────────── Программа на Rust ───────────────────┐
 │  Хранилище версий          │  Сравнение                 │
 │  git + LFS, файлы/ссылки   │  OpenCascade через FFI     │
 │  история, варианты, откат  │  числа, подсветка, дерево  │
 │────────────────────────────┼────────────────────────────│
 │  Заметки и ссылки          │  API и MCP                 │
 │  Markdown, [[ссылки]]      │  синхронизация с сервером  │
 └──────────────────────────────────────────────────────────┘
        ▲▼                   │                    ▲▼
 Папка проекта          Окно программы       Сервер проекта
 STEP, YAML, Markdown   (egui, в nonius.exe) Forgejo: роли, блокировки
```

Какой файл за что отвечает — в [CODEMAP.md](CODEMAP.md).

## Папка проекта

```
мой-проект/
├── project.yaml            # имя, участники, роли, допуски сравнения
├── AGENTS.md               # описание проекта и правила для ИИ
├── .gitattributes          # бинарные файлы CAD через Git LFS
├── parts/<имя>/
│   ├── meta.yaml           # масса, объём, габариты, материал, свойства
│   ├── tree.yaml           # дерево построения (если из SolidWorks)
│   ├── model.step          # геометрия, есть всегда
│   ├── model.sldprt        # исходник
│   ├── preview.png
│   └── docs/               # чертежи, PDF, DXF
├── assemblies/<имя>/       # то же для сборок
└── notes/                  # заметки Markdown со ссылками [[деталь@v3#Фича]]
```

Каждый файл данных начинается с `schema: N` (`nonius_core::schema`). Программа читает свою и более старые схемы (через миграции) и отказывается читать более новые, чтобы не испортить файл.

## Ядро и модули

Ядро (`nonius-core`) — только формат проекта, схемы, имена, точки расширения и реестр. Всё остальное — модули, и встроенные подключаются так же, как сторонние.

| Точка (`ExtensionPoint`) | Трейт | Что делает | Примеры |
|---|---|---|---|
| `GeometrySource` | `GeometrySource` | файл → паспорт версии (`meta.yaml`) | STEP через OpenCascade, SLDPRT без SolidWorks |
| `TreeSource` | `TreeSource` | файл → дерево построения | аддин SolidWorks, FreeCAD |
| `Comparator` | `Comparator` | различия двух версий | паспорт (встроен: `meta-compare`), геометрия, дерево, BOM |
| `Renderer` | `Renderer` | картинки и GIF изменений | цветная подсветка |
| `Exporter` | `Exporter` | файлы из версии | DXF, PDF, STL |
| `Events` | `EventHandler` | реакция на события | уведомления в Telegram, проверки перед утверждением |
| `Ui` | — | панели интерфейса | подключаются веб-интерфейсом |

Правила, чтобы модули ничего не ломали:
- у модуля `ModuleManifest`: id, название, версия, версия API, точки, права;
- реестр подключает модуль только к точкам из манифеста и проверяет версию API (`API_VERSION`, `MIN_API_VERSION`);
- права явные (`Permission`);
- для каждой точки есть контрактная проверка в `nonius_core::contract`; модуль, прошедший её, совместим;
- ядро не знает о конкретных модулях; отключение модуля не теряет данные — они в открытых форматах.

Способы подключения: встроенный крейт (сейчас), внешний процесс по JSON-RPC и WASM-модуль (позже).

## Хранилище версий (`nonius-store`)

Версия детали — коммит git, который меняет только папку этой детали. В сообщении — описание и служебные строки:

```text
кронштейн v3: толщина 4 → 5 мм под новый вал

Nonius-Item: кронштейн
Nonius-Version: v3
```

- номер версии у каждой детали свой и растёт на 1;
- бинарные файлы идут через Git LFS по `.gitattributes`, файлы версии читаются `git cat-file --filters`;
- откат (`restore`) создаёт новую версию с содержимым старой — история не переписывается;
- используется системный `git`, а не библиотека: он уже умеет LFS и ведёт себя одинаково у всех.

## Цвета подсветки

`ChangeKind` в отчёте сравнения привязан к цвету: `Added` — зелёный, `Removed` — красный, `Moved` — жёлтый, без изменений — приглушённый.

## Окно программы (`nonius-gui`)

Двойной щелчок по `nonius.exe` открывает окно: детали проекта, история версий, деталь в 3D с цветной подсветкой изменений, сохранение новой версии. Окно — часть того же exe, без браузера, ничего не нужно ставить. Командная строка работает как прежде.

### Крейты и границы

```
 nonius-cli (exe) ──┬── nonius-gui ──┐       окно: egui + wgpu
   команды,         │                ├── nonius-app     действия программы
   сборка реестра   └────────────────┘        │
   модулей                                    ├── nonius-store   версии: git + LFS
                                              ├── nonius-scene   модель сцены и glTF
                                              └── nonius-core    формат, схемы, точки расширения
 модули: nonius-occt (OpenCascade), nonius-step … — подключаются к реестру из nonius-core
```

| Крейт | Что внутри | Чего не знает |
|---|---|---|
| `nonius-core` | формат проекта, схемы, точки расширения, реестр | окна, git, OpenCascade |
| `nonius-scene` | модель сцены: слои, сетки, места изменений, подписи; запись и чтение glTF (`.glb`) | OpenCascade, egui, git |
| `nonius-app` | **действия**: открыть проект, детали, история, сравнить (с кэшем и в фоне), импортировать модель, сохранить версию, откатить, выгрузить, задать материал | окна и консоли |
| `nonius-gui` | окно: панели, 3D-вид, мышь, фоновые задачи, тексты интерфейса | OpenCascade и git: всё через `nonius-app` |
| `nonius-cli` | разбор команд и печать; собирает реестр со встроенными модулями и передаёт его в `nonius-app`; без команды открывает окно | — |

Правила:
- CLI, окно, а позже MCP и сервер вызывают **одни и те же действия** `nonius-app`. Логика не дублируется: что умеет окно, умеет и команда, и ИИ.
- `nonius-core` не тянет графику: в ядре нет egui, wgpu и glTF.
- Отрисовщик (`Renderer`) отдаёт сцену файлом `changes.glb`. Окно читает его через `nonius-scene` и не знает, каким модулем и из какого CAD-формата он сделан. Сменить движок отрисовки окна или добавить новый формат — работа одного крейта.
- Будущие панели модулей (калькулятор массы, раскрой листа) подключаются к точке `Ui` через трейт панели в `nonius-gui`. Трейт появится вместе с первым таким модулем.

### Модель сцены (`nonius-scene`)

Сцена — то, что показывается в 3D:
- **место** — кусок материала с ролью, сеткой и объёмом. Роли: `after` (новая версия целиком, «стало»), `before` (старая версия целиком, «было»), `added`, `removed`, позже `moved`. Каждый отдельный кусок добавленного или убранного материала — своё место: по списку мест окно приближает к изменению;
- цвет роли один для картинок, 3D и интерфейса (`Role::color`);
- сетки в мм, оси — как в исходном файле (у SolidWorks Y вверх).

На диске сцена хранится в стандартном glTF 2.0 (`.glb`): узел на каждое место, роль и объём лежат в `extras`. Старая версия целиком лежит во второй сцене glTF, поэтому сторонние программы (Средство 3D-просмотра Windows, Blender) показывают «стало» с цветными изменениями.

**Формат сцены и формат кэша — публичный контракт с номером версии**, как схемы файлов проекта:
- в `asset.extras.nonius_scene` у `.glb` записан номер формата сцены; в `cache.yaml` — `schema: N`;
- новые поля добавляются так, чтобы старые программы их пропускали; несовместимое изменение повышает номер и идёт с миграцией и тестом на старый файл;
- более новый формат программа не читает и объясняет, что пора обновиться;
- `nonius_scene::contract` проверяет сцену любого модуля-отрисовщика (роли, сетки, единицы, номер формата). Её прогоняют тесты `nonius-scene` без OpenCascade и тесты каждого отрисовщика; в репозитории лежит образец `.glb` каждой версии формата, и новые программы обязаны его читать.

### Поток данных при сравнении

```
окно: выбрали «было» и «стало»
  → nonius-app: ключ кэша = хеш обоих model.step + версии модулей
      ├─ есть в кэше → сразу отчёт и сцена
      └─ нет → фоновая задача с ходом выполнения и отменой:
            реестр: сравнения (отчёт) ‖ отрисовщик сцены (changes.glb)
            → записать в кэш
  → окно: 3D, места изменений, числа
```

Кэш лежит в `.git/nonius/cache/` и в историю не попадает. Описание кэша `cache.yaml` начинается с `schema: N` и меняется только с миграцией, как все схемы. Незнакомую или битую запись программа пересчитывает и ничего не теряет.

### Тексты интерфейса

Все надписи окна собраны в одном модуле `crates/nonius-gui/src/texts.rs`: таблица строк, русский по умолчанию. Код окна берёт надписи только оттуда. Перевод на другой язык — ещё одна такая таблица; если языков станет много, таблица переедет в файлы готового формата (Fluent), а код окна при этом не поменяется. Сторонняя библиотека переводов сейчас не нужна: лишние зависимости в одном exe ни к чему.

### Мышь и клавиши — как в SolidWorks

| Действие | Мышь | Клавиши |
|---|---|---|
| вращать | средняя кнопка (или левая по пустому месту) | стрелки |
| сдвигать | Ctrl + средняя | Ctrl + стрелки |
| приближать | колесо (к курсору), Shift + средняя | — |
| показать целиком | двойной щелчок средней | F |
| виды | куб видов | Ctrl+1 спереди … Ctrl+7 изометрия |

### Проверки

- `nonius-scene` и `nonius-app`: обычные тесты без окна (сцена ↔ glTF, кэш и его миграции, действия на временном проекте).
- `nonius-gui`: тесты интерфейса без экрана ([egui_kittest](https://crates.io/crates/egui_kittest)) и проверка 3D-отрисовки в память. На Windows в CI она идёт через программную отрисовку WARP; там, где видеоадаптера нет совсем, тест пропускается с пояснением.
- Ручная проверка на ПК Владимира перед мержем.

### Ограничения версий

`eframe`/`egui` 0.32 — последняя версия, которая собирается на Rust 1.85 (минимальная версия проекта). Переход на новые версии вместе с повышением минимальной версии Rust делается отдельным PR.

## Стек

| Часть | Технология |
|---|---|
| Ядро, CLI, сервер | Rust |
| Геометрия | OpenCascade через FFI (отдельный крейт) |

| Сервер проекта | Forgejo |
| Доступ для ИИ | MCP поверх того же API |

## Этапы

1. Хранилище и история: git + LFS, импорт STEP, версии, откат. ← **готово** (`nonius-store`, `nonius-step`)
2. Геометрическое сравнение и цветная подсветка.
3. Аддин SolidWorks.
4. Дерево построения и его diff.
5. Доступ для ИИ (MCP).
6. Сервер и совместная работа: утверждение лидером, блокировки.
7. Заметки. 8. Варианты. 9. Сборки. 10. Публичные проекты и релиз.
